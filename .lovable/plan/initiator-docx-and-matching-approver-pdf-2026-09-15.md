# Initiator DOCX and Matching Approver PDF

## Confirmed outcome

- The Initiator continues to receive an editable Microsoft Word `.docx` working document.
- The latest uploaded/saved Initiator document remains versioned privately against its eNFA number.
- Approvers see a read-only PDF containing the complete mapped header, Detailed Description, tables, embedded images, Approvals, and Comments.
- The PDF is generated by the application, as selected; no Microsoft connector, Word Online, DMS integration, or new SAP API will be added.
- Existing Create, Edit, Approve, Reject, Back to Initiator, Clarification, attachments, SAP payloads, and permissions remain unchanged.

## Current gap to correct

- The Initiator DOCX and Approver PDF are currently produced through separate renderers: the DOCX generator builds Word elements, while the Approver PDF captures the web Print Form as one tall image and slices it across pages.
- A revised DOCX currently synchronizes only the Detailed Description back into the application. Whole-document changes to headers, Approvals, or Comments are not imported.
- Image sizing is interpreted differently between Word and the web preview. The uploaded `ENFA-100123-working.docx` contains a 640×505 description image displayed at approximately 6.67 inches wide, which explains the oversized image shown in the reference screenshot.

## Implementation

### 1. Use one canonical document model

- Build one normalized Print Form model from the existing SAP row, locally saved draft, approver chain, comments, and latest Initiator Detailed Description.
- Feed that same normalized model into both DOCX generation and the Approver PDF view so field values, ordering, labels, tables, comments, and images cannot diverge.
- Keep Subject separate and keep Detailed Description only in its designated section.

### 2. Preserve the reference Word structure

- Align DOCX page size, margins, header rows, bands, borders, fonts, spacing, Approvals grid, and Comments section with the uploaded reference Word document.
- Preserve rich-description paragraphs, bold/italic/underline text, alignment, lists, tables, merged-cell metadata where supported, and embedded images.
- Normalize every image to its intended displayed dimensions, preserve aspect ratio, and cap it to the printable content width so it cannot expand to the oversized result shown in the screenshot.
- Continue embedding image bytes in the DOCX; never retain temporary browser or external image links.

### 3. Keep the Initiator workflow editable

- Keep **Download DOCX** and **Upload Revised DOCX** for Initiators and continue creating a new private version for each save/upload.
- On upload, validate the eNFA identity and DOCX package, then extract the Detailed Description—including supported tables, formatting, alignment, and embedded images—back into the shared document model.
- Reopen the latest saved version for subsequent Initiator revisions, including after clarification.
- Do not expose DOCX editing controls to Approvers.

### 4. Generate the Approver PDF from the shared content

- Replace the current single-canvas slicing with page-aware application PDF rendering based on the same normalized model used for the DOCX.
- Render the full document in order: reference header, mapped fields, Detailed Description, Approvals, and Comments.
- Keep table rows and images within page bounds, preserve practical column widths and alignment, and continue content cleanly across A4 pages without clipping.
- Ensure the Approver Print Form and downloaded PDF always reload the latest saved Initiator description/version before rendering.

### 5. Verification

- Use the uploaded `ENFA-100123-working.docx` as the regression reference.
- Verify normal and long text, formatting, pasted Word/Excel tables, alignment, multiple images, Approvals, and Comments in both outputs.
- Open the generated DOCX in Word, upload the revised file, then confirm the Approver PDF shows the same supported content with no missing, stretched, cropped, or page-split elements.
- Test multi-page output and clarification/revision flow.
- Regression-test Create, Edit, Approve, Reject, Back to Initiator, Clarification, attachments, and existing SAP requests.

## Fidelity boundary

Because the selected PDF is application-generated rather than converted by Microsoft Word, it can match the controlled eNFA template and all supported mapped/rich-description content, but it cannot reproduce arbitrary whole-document Word edits or Word’s pagination engine pixel-for-pixel. Changes outside the designated Detailed Description remain application-controlled, as in the current workflow.
